0 Preparar o ambiente

Antes de escrever qualquer teste, confirme que o projeto roda. Abra o terminal na pasta crm/ e execute:

npm install
npm test
  • npm install baixa o Vitest, o jsdom e o json-server (só na primeira vez).
  • npm test liga o Vitest em modo observação: ele roda os testes de novo sempre que você salva um arquivo. Para rodar uma vez e sair use npm run test:run.
  • Para testar o usuario.js você não precisa ligar o json-server: os testes usam uma API falsa em memória (api-falsa.js).

Regra do projeto: nada de async/await. As promessas são encadeadas com .then().

1 Ler o código que será testado

Um bom teste começa pela leitura do código (visão de caixa branca): é lendo que descobrimos todos os caminhos que precisam de teste. Este é o src/usuario.js:

/** Cadastro de usuário (login). Dados no formato {id, login, senha, status}. */

import { criarTelaCadastro } from './tela.js';

export const COLECAO_USUARIOS = 'usuarios';
export const STATUS_ATIVO = 1;
export const STATUS_INATIVO = 0;
export const CAMPOS_USUARIO = [
  { nome: 'login', rotulo: 'Login', tipo: 'text' },
  { nome: 'senha', rotulo: 'Senha', tipo: 'password' },
  { nome: 'status', rotulo: 'Status (1=ativo, 0=inativo)', tipo: 'number' },
];
const COLUNAS_USUARIO = [
  { chave: 'id', rotulo: 'ID' },
  { chave: 'login', rotulo: 'Login' },
  { chave: 'status', rotulo: 'Status' },
];

/**
 * @param {{status: number}} usuario - Usuário.
 * @returns {boolean} true quando o status é 1 (ativo).
 */
export function estaAtivo(usuario) {
  return usuario.status === STATUS_ATIVO;
}

/**
 * Confere os dados de um usuário.
 * @param {{login: string, senha: string, status: number}} usuario - Dados.
 * @returns {string[]} Lista de erros (vazia quando está tudo certo).
 */
export function validarUsuario(usuario) {
  const erros = [];
  if (!usuario.login) erros.push('Login obrigatório');
  if (!usuario.senha) erros.push('Senha obrigatória');
  const statusValido = usuario.status === STATUS_ATIVO || usuario.status === STATUS_INATIVO;
  if (!statusValido) erros.push('Status deve ser 1 ou 0');
  return erros;
}

/**
 * Cria o repositório de usuários sobre a API injetada.
 * @param {object} api - API injetada (json-server).
 * @returns {{cadastrar: Function, listar: Function, buscarPorLogin: Function}} Repositório.
 */
export function criarRepositorioUsuarios(api) {
  /** @param {string} login - Login procurado. @returns {Promise<object|null>} Usuário ou null. */
  function buscarPorLogin(login) {
    return api
      .listar(COLECAO_USUARIOS)
      .then((lista) => lista.find((usuario) => usuario.login === login) ?? null);
  }

  /**
   * @param {object} dados - Dados do novo usuário.
   * @returns {Promise<object>} Usuário salvo (recusa se inválido ou se o login já existe).
   */
  function cadastrar(dados) {
    const erros = validarUsuario(dados);
    if (erros.length > 0) return Promise.reject(new Error(erros.join('; ')));
    return buscarPorLogin(dados.login).then((existente) => {
      if (existente) throw new Error('Login já cadastrado');
      return api.criar(COLECAO_USUARIOS, dados);
    });
  }

  return { cadastrar, buscarPorLogin, listar: () => api.listar(COLECAO_USUARIOS) };
}

/**
 * Monta a tela de usuários.
 * @param {object} api - API injetada (json-server).
 * @returns {HTMLElement} Seção da tela.
 */
export function criarTelaUsuario(api) {
  const repositorio = criarRepositorioUsuarios(api);
  return criarTelaCadastro({
    titulo: 'Usuários',
    campos: CAMPOS_USUARIO,
    colunas: COLUNAS_USUARIO,
    aoSalvar: (dados) => repositorio.cadastrar(dados),
    aoListar: () => repositorio.listar(),
  });
}

3 Criar o arquivo e importar as ferramentas

Crie o arquivo src/usuario.test.js (mesma pasta e mesmo nome do código, mais .test.js) e comece pelos import:

// 3.1 Ferramentas do Vitest: describe agrupa, it é um caso de teste, expect confere o resultado,
//     beforeEach roda antes de cada teste e vi cria mocks (substitutos controlados).
import { describe, it, expect, beforeEach, vi } from 'vitest';
// 3.2 A API falsa guarda os dados em memória: o teste não precisa do json-server ligado.
import { criarApiFalsa } from './api-falsa.js';
// 3.3 O que vamos testar (o nome do arquivo de teste é o do código + ".test.js").
import {
  criarRepositorioUsuarios, criarTelaUsuario, estaAtivo, validarUsuario,
} from './usuario.js';

// 3.4 Dado de apoio: um usuário válido que várias vezes serve de ponto de partida.
const USUARIO_OK = { login: 'ana', senha: '123', status: 1 };
  • describe agrupa os testes de uma mesma unidade; it é um caso de teste.
  • expect(valor).matcher(esperado) é a conferência (o Assert).
  • vi é a caixa de ferramentas de mocks do Vitest.
  • A API falsa troca o json-server por dados em memória: o teste fica rápido e não depende de rede.

4 Testar uma função simples: estaAtivo (padrão AAA)

Todo teste segue três etapas: Arrange (preparar), Act (agir) e Assert (conferir). Veja os comentários no código:

// PASSO 4 — Função simples e síncrona: estaAtivo (caminhos: status 1 e status diferente de 1)
describe('estaAtivo', () => {
  it('é verdadeiro quando o status é 1', () => {
    // Arrange (preparar): o usuário que vamos avaliar
    const usuario = { login: 'ana', senha: '123', status: 1 };

    // Act (agir): chamamos a função exatamente uma vez
    const resultado = estaAtivo(usuario);

    // Assert (conferir): toBe é o matcher certo para um valor simples (true/false)
    expect(resultado).toBe(true);
  });

  it('é falso quando o status é 0 (inativo)', () => {
    expect(estaAtivo({ status: 0 })).toBe(false);
  });

  // Este teste "mata" o mutante `>=` do passo 10: só o status 1 é ativo, 2 não é
  it('é falso para qualquer outro status, como 2', () => {
    expect(estaAtivo({ status: 2 })).toBe(false);
  });
});
  • Um it para cada caminho da função: aqui, status 1 e status 0.
  • toBe serve para valores simples (true, números, textos).
  • Cada teste é independente: não depende da ordem nem do resultado de outro.

5 Testar a validação: toEqual, toContain e it.each

validarUsuario devolve uma lista de erros. Aqui entram os valores-limite: não basta testar o valor certo, teste também os vizinhos errados.

// PASSO 5 — Validação: validarUsuario devolve uma LISTA de erros (lista vazia = tudo certo)
describe('validarUsuario', () => {
  it('devolve lista vazia para um usuário válido', () => {
    // toEqual compara o CONTEÚDO de arrays e objetos (toBe compararia a referência)
    expect(validarUsuario(USUARIO_OK)).toEqual([]);
  });

  it('exige login e senha', () => {
    const erros = validarUsuario({ login: '', senha: '', status: 1 });

    expect(erros).toEqual(['Login obrigatório', 'Senha obrigatória']);
  });

  // Valores-limite: it.each repete o mesmo teste para vários valores (%s vira o valor)
  it.each([2, -1, '1', undefined])('recusa o status %s (só 1 ou 0 valem)', (status) => {
    // toContain confere se UM item está dentro da lista, sem exigir a lista inteira
    expect(validarUsuario({ ...USUARIO_OK, status })).toContain('Status deve ser 1 ou 0');
  });

  it.each([0, 1])('aceita o status %s', (status) => {
    expect(validarUsuario({ ...USUARIO_OK, status })).toEqual([]);
  });
});
  • toEqual compara o conteúdo de listas e objetos; toBe compararia a referência.
  • toContain confere se um item está na lista, sem exigir a lista toda.
  • it.each([...]) repete o mesmo teste para vários valores e evita copiar e colar.
  • Use o matcher mais específico: toEqual([]) diz mais que toBeFalsy().

6 Testar o repositório com promessas (sem await)

O banco responde de forma assíncrona (fetch). Como o projeto não usa await, cada teste devolve (return) a promessa encadeada com .then:

// PASSO 6 — Repositório: o banco responde de forma assíncrona (fetch), então cada teste
// DEVOLVE (return) a promessa encadeada com .then. Sem o return o teste termina antes
// do resultado chegar e "passa" sem conferir nada.
describe('repositório de usuários', () => {
  let repositorio;
  let api;

  // beforeEach: um banco novo e vazio antes de CADA teste, para um não depender do outro
  beforeEach(() => {
    api = criarApiFalsa();
    repositorio = criarRepositorioUsuarios(api);
  });

  it('cadastra e depois encontra o usuário pelo login', () => {
    return repositorio
      .cadastrar(USUARIO_OK) // Arrange + Act
      .then(() => repositorio.buscarPorLogin('ana')) // Act
      .then((usuario) => {
        // Assert: o banco acrescentou o id sozinho
        expect(usuario).toEqual({ ...USUARIO_OK, id: 1 });
      });
  });

  it('devolve null quando o login não existe', () => {
    return repositorio.buscarPorLogin('ninguem').then((usuario) => {
      expect(usuario).toBeNull();
    });
  });

  it('recusa login repetido', () => {
    const repetido = repositorio
      .cadastrar(USUARIO_OK)
      .then(() => repositorio.cadastrar(USUARIO_OK));

    // rejects + toThrow: a promessa deve ser RECUSADA com esta mensagem (sem await)
    return expect(repetido).rejects.toThrow('Login já cadastrado');
  });

  it('recusa dados inválidos e não grava nada', () => {
    const invalido = repositorio.cadastrar({ login: '', senha: '', status: 5 });

    return expect(invalido)
      .rejects.toThrow('Login obrigatório')
      .then(() => repositorio.listar())
      .then((lista) => expect(lista).toHaveLength(0));
  });
});
  • Sem o return o teste termina antes do resultado chegar e passa sem conferir nada (o erro mais comum).
  • beforeEach cria um banco novo antes de cada teste: nenhum teste enxerga os dados do anterior.
  • expect(promessa).rejects.toThrow('mensagem') confere uma recusa (o catch do cadastro).
  • O teste de dados inválidos confere duas coisas: a recusa e que nada foi gravado.

7 Isolar a dependência com mock (vi.fn)

Para provar como a API foi usada, trocamos a API por um mock: uma função falsa que devolve o que o teste manda e registra como foi chamada.

// PASSO 7 — Mock: trocamos a API por um substituto para PROVAR como ela foi usada.
describe('repositório de usuários com mock da API', () => {
  it('não chama api.criar quando o login já existe', () => {
    // vi.fn().mockResolvedValue(x): função falsa que devolve uma promessa já resolvida com x
    const api = {
      listar: vi.fn().mockResolvedValue([{ id: 1, ...USUARIO_OK }]),
      criar: vi.fn(),
    };

    return criarRepositorioUsuarios(api)
      .cadastrar(USUARIO_OK)
      .catch(() => {})
      .then(() => {
        // not.toHaveBeenCalled: garante que NADA foi gravado
        expect(api.criar).not.toHaveBeenCalled();
      });
  });

  it('chama api.criar na coleção "usuarios" com os dados informados', () => {
    const api = {
      listar: vi.fn().mockResolvedValue([]),
      criar: vi.fn().mockResolvedValue({ id: 1, ...USUARIO_OK }),
    };

    return criarRepositorioUsuarios(api)
      .cadastrar(USUARIO_OK)
      .then(() => {
        // toHaveBeenCalledWith confere os argumentos da chamada
        expect(api.criar).toHaveBeenCalledWith('usuarios', USUARIO_OK);
      });
  });
});
  • vi.fn().mockResolvedValue(x) devolve uma promessa já resolvida com x.
  • not.toHaveBeenCalled() prova que nada foi gravado quando o login já existe.
  • toHaveBeenCalledWith('usuarios', dados) prova que a gravação usou a coleção e os dados certos.
  • O repositório recebe a api por parâmetro (injeção de dependência): é isso que torna o mock possível.

8 Testar a tela (DOM) com jsdom

O Vitest roda os testes com o jsdom, um navegador de mentira: dá para criar elementos, procurar com querySelector e disparar eventos sem abrir janela.

// PASSO 8 — Tela (DOM): o Vitest usa o jsdom, um "navegador de mentira" sem abrir janela.
describe('criarTelaUsuario', () => {
  it('lista o usuário cadastrado sem mostrar a senha', () => {
    const api = criarApiFalsa();

    return criarRepositorioUsuarios(api)
      .cadastrar(USUARIO_OK)
      .then(() => {
        const tela = criarTelaUsuario(api);

        // A tabela é desenhada depois que a lista chega: vi.waitFor repete o expect até passar
        return vi.waitFor(() => {
          const linha = tela.querySelector('tbody').rows[0];
          expect(linha.textContent).toContain('ana');
          expect(linha.textContent).not.toContain('123');
        });
      });
  });
});
  • A tabela só é desenhada depois que a lista chega; vi.waitFor repete o expect até passar (ou estourar o tempo).
  • not.toContain('123') garante uma regra de segurança: a senha nunca aparece na tela.

9 Rodar e ler o resultado

npx vitest run src/usuario.test.js

Resultado esperado: todos os testes com ✓ e uma linha parecida com Tests N passed (N). Se algum falhar, leia o bloco vermelho:

  • Expected / Received: o que você esperava e o que a função devolveu.
  • A linha com ❯ src/usuario.test.js:NN aponta o teste que falhou.
  • Falhou por timeout ou passou rápido demais? Confira se esqueceu o return da promessa.

10 Dinâmica: o mutante sobrevivente

Um teste só tem valor se falha quando o código está errado. Em dupla, altere o usuario.js e rode os testes:

Mutante (alteração)Quem deve falhar
Trocar === STATUS_ATIVO por >= STATUS_ATIVO em estaAtivoO teste "é falso para qualquer outro status, como 2" (sem ele, o mutante sobrevive)
Apagar a linha da validação da senha"exige login e senha"
Remover a linha if (existente) throw new Error('Login já cadastrado') do cadastrar"recusa login repetido" e o mock de criar não chamado
Exibir a coluna senha na tela"sem mostrar a senha"

Se nenhum teste falhar, o mutante sobreviveu: escreva o teste que faltava. Depois desfaça a alteração (git checkout src/usuario.js).
